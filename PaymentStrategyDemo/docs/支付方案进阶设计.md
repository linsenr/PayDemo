# 支付方案进阶设计

## 项目结构

当前项目仍是一个 .NET 项目，按 DDD 常见职责边界组织源文件：

```text
Domain/
  Payments/                  支付单与支付状态
Application/
  Payments/
    Abstractions/            用例依赖的端口和仓储接口
    Models/                  按类型拆分的请求、渠道结果与回调模型
    Services/                支付用例、路由策略及路由配置
Infrastructure/
  DependencyInjection/       PaymentServiceCollectionExtensions 依赖注入组合根
  Payments/
    Persistence/             内存仓储示例
    Security/                回调验签实现
    Strategies/               支付渠道适配器
  Payments/LegacyPaymentFactory.cs  暂时保留的旧工厂注释代码
Presentation/
  Console/                   控制台演示入口
```

项目暂未拆分成多个程序集，目录和命名空间已对应这些边界。`Domain` 不依赖应用层或基础设施；应用层通过接口依赖渠道和仓储能力；基础设施实现这些接口。

## 1. 从固定选择扩展为渠道路由

项目已增加 `IPaymentRouter` / `PaymentRouter`，按支付请求、渠道支持币种、禁用配置及渠道优先级选择支付方式。

已实现的路由行为：

- CNY 小额订单（不超过配置阈值）把微信放在首选位置，仍按币种配置保留备选渠道。
- 其他请求按币种配置的优先顺序选择渠道。
- 禁用或不支持请求币种的渠道会被跳过，并尝试下一个候选渠道。
- 显式指定首选渠道时只尝试该渠道，不可用时明确失败，避免意外切换支付渠道。
- 未配置的币种明确失败，不按注册顺序或字母顺序任意选渠道。
- 路由器启动时校验策略类型、支持币种和路由配置，并复制配置，防止后续外部修改影响运行中的路由行为。

地区和订单类型已进入请求模型，但当前还未用于渠道选择。若要按这两项增加规则，应把规则放进路由组件并补充对应场景验证。

## 2. 增加完整的支付流程阶段

目前 `PaymentService` 协调以下流程：

1. 校验并规范化支付请求，通过路由器选择渠道。
2. 先创建本地支付记录，再将状态推进到 `Processing` 并调用渠道。
3. 渠道返回交易号和后续操作信息后，记录 `Pending` 等状态；调用异常会保留 `Processing`，因为超时不代表渠道一定未受理。
4. 回调按本地支付记录找到原渠道，先由渠道适配器验证签名，再核对渠道与交易号并更新最终状态。
5. 回调事件按渠道和事件 ID 去重，终态不可被迟到的渠道响应或后续通知覆盖。

新增的主要模型包括 `PaymentOrder`、`PaymentInitiationResult` 和 `PaymentCallback`。`InMemoryPaymentOrderStore` 只用于单进程演示；生产环境必须替换成具备事务、唯一约束和持久化幂等事件记录的数据库仓储。真实渠道还需要实现对应的原始回调报文验签、时间戳/重放防护和渠道状态映射。当前 HMAC 验签示例使用 `PAYMENT_CALLBACK_KEY_<渠道类型>` 环境变量，不配置密钥时拒绝回调；它不是任何真实支付渠道的完整适配器。

支付渠道策略负责发起支付和验证渠道回调，`PaymentService` 负责流程协调，仓储负责订单状态及回调幂等记录。渠道调用超时后订单保持处理中，生产系统还需要渠道查询或对账任务来收敛状态。

## 3. 引入支付状态机

为订单定义明确的支付状态，例如：

`Created → Processing → Pending → Succeeded / Failed / Expired`

已在 `Domain/Payments/PaymentStateMachine.cs` 实现集中状态转换规则：允许 `Created → Processing`、`Processing → Pending / Succeeded / Failed / Expired`，以及 `Pending → Succeeded / Failed / Expired`。同状态转换视为幂等操作；终态之间以及从终态回到处理中均不允许转换。

内存仓储在推进处理中状态、记录渠道发起结果和应用回调时都调用该状态机。重复的同状态成功通知安全返回未处理；已成功订单收到失败或过期通知时会明确拒绝，不会覆盖成功状态。迟到的渠道发起响应仍不会覆盖已由回调确认的终态。未来增加主动查询或重试时，应通过同一状态机校验结果，不能直接写入状态字段。

当前示例尚未实现主动查询和重试用例。建议后续测试覆盖允许转换、非法终态回退、重复成功通知、成功后收到失败通知，以及回调先于渠道响应到达等场景。生产仓储还需将状态转换与回调事件去重放在同一事务中，并通过并发控制防止多实例同时推进状态。

## 4. 描述支付渠道能力

已通过独立的 `IPaymentQuery` 演示支付查询能力。支付宝策略实现该接口，微信策略不实现；`PaymentService.QueryPaymentStatusAsync` 在调用渠道前检查能力，不支持时明确返回 `NotSupportedException`。查询结果通过仓储应用，并继续经过支付状态机校验，避免查询结果绕过状态规则。

渠道原有的 `SupportedCurrencies` 描述币种范围，路由器据此选择渠道。退款、部分退款和预授权可按相同方式分别建模为独立能力接口；只让实际支持该操作的渠道实现对应接口，不应把所有可选操作都塞进基础 `IPayment`。当前支付宝查询实现仅返回模拟状态，接入真实渠道时需替换为官方查询 API 和状态映射。

建议补充查询能力支持与不支持、非法渠道状态、查询结果触发非法状态转换等测试场景。

## 5. 使用装饰器组合通用行为

已增加 `PaymentObservabilityDecorator`，在渠道策略外层统一记录调用次数、耗时直方图和 `Activity` 诊断活动，覆盖发起支付、回调验签和主动查询。指标只包含渠道类型、操作和结果，不包含订单号、回调报文或签名。DI 注册为具体渠道策略加装饰器；查询渠道使用专用的 `PaymentQueryObservabilityDecorator` 保留 `IPaymentQuery` 可选能力，避免装饰后丢失能力接口。

当前没有加入自动重试。支付请求的超时可能发生在渠道已受理但响应尚未返回时；没有渠道幂等键和结果查询/对账机制时自动重试有重复扣款风险。生产接入应先配置渠道 HTTP 客户端超时和取消，再依据渠道幂等协议增加有限重试、熔断及指标导出。建议验证装饰器对正常调用、异常传播、查询能力保留和指标标签不含敏感数据的行为。

## 6. 增加模拟渠道和失败场景

已增加 `PaymentSimulation` 配置与 `SimulatedPaymentDecorator`，可针对指定渠道模拟正常发起、渠道拒绝和超时。渠道拒绝返回 `Failed` 结果；超时抛出 `TimeoutException`，演示入口仍能读取已保存的订单并展示 `Processing` 状态。`DuplicateCallbackDelivery` 可让演示入口将同一签名回调投递两次，验证幂等处理。

示例配置位于 `appsettings.json`，默认关闭失败模拟，维持原有正常支付流程。可将 `InitiationMode` 设为 `Decline` 或 `Timeout`，并通过 `TimeoutDelayMilliseconds` 调整模拟等待时间。模拟装饰器仅用于演示，不能替代真实支付渠道适配器。建议验证默认流程、拒绝进入 `Failed`、超时保留 `Processing`、重复回调只处理一次及取消令牌中止模拟等待。

## 7. 让渠道实现可插拔

已将渠道注册拆分为显式模块入口：`AlipayPaymentModule.AddAlipayPaymentChannel()` 和 `WechatPaymentModule.AddWechatPaymentChannel()`。`AddPaymentStrategy()` 负责调用这些模块并注册路由器、仓储和验签服务；每个渠道模块集中注册自身策略以及对应的观测、模拟装饰器。支付宝模块保留 `IPaymentQuery` 可选能力，微信模块不暴露该能力。

新增渠道时，添加自己的注册模块，让它注册 `IPayment` 实现和所需能力接口，再由组合根显式调用模块入口；同时在币种路由配置中增加该渠道。这样路由器仍可从 `IEnumerable<IPayment>` 收集渠道，无需修改路由算法。当前规模采用显式注册，尚未引入程序集扫描或运行时插件加载，便于追踪启动注册和排查缺失配置。

建议验证每个模块单独注册后能被路由器发现、重复渠道类型仍在启动时明确报错，以及可选能力在装饰后仍正确暴露。

## 生产化前的工作

当前实现用于演示流程结构，不能直接承载真实交易：状态和幂等事件只保存在内存里，模拟渠道也不连接支付机构。生产接入前需要实现持久化、各渠道官方验签协议、幂等和对账流程，并为状态转换、重复回调、非法回调和渠道超时补充自动化测试。
